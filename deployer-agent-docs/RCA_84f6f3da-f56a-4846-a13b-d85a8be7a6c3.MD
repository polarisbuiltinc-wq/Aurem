# RCA — launch-pad-237 build failure (frontend-build-push, node/vite engine mismatch)

## Verdict
**Source-class failure. Not fixable from the deployment manifest.** Requires a one-line change in `frontend/package.json` + a yarn.lock regen, then redeploy.

## Failed step
`build_image` → Cloud Build step #8 `frontend-build-push` (runs `build-frontend-artifacts.sh` on the `customer-apps-node-base` image). Reproduced identically on two runs:
- `84f6f3da-f56a-4846-a13b-d85a8be7a6c3` (original)
- `cc285bb3-69c8-4b80-90f5-269e41a60a78` (my manifest retry)

## Terminating error (verbatim, repeated across all 3 yarn retries)
```
error vite@7.3.6: The engine "node" is incompatible with this module.
Expected version "^20.19.0 || >=22.12.0". Got "20.18.1"
error Found incompatible module.
```

## Root cause
The Session-4 P1 batch bumped the frontend test tooling. `frontend/package.json` correctly pins the DIRECT dependency `"vite": "^6.4.3"`, but the upgraded test deps pull a SECOND, transitive vite:

- `vitest@3.2.6` and its child `vite-node@3.2.4` both declare a dependency `vite "^5.0.0 || ^6.0.0 || ^7.0.0-0"` (confirmed in `frontend/yarn.lock`, lines 5392 & 5459).
- yarn resolves that open range to the highest available match → **`vite@7.3.6`**.
- `vite@7.3.6` requires node `^20.19.0 || >=22.12.0`. The build's node base image (`customer-apps-node-base:v0.3.77`) ships **node 20.18.1**, so `yarn install` aborts with "Found incompatible module."

Net: two vites in the tree — `6.4.3` (direct, node-20.18 OK) and `7.3.6` (transitive via vitest, needs node ≥20.19). The transitive one fails the engine check and kills the install.

## Why I could not fix it from the deployment side
The node version comes from the platform-injected `FRONTEND_IMAGE`. I removed the stale `FRONTEND_IMAGE: ...node-base:v0.3.77` pin from `config.yaml` so the platform would inject its current node base — but the retried build's step #8 **still ran on node 20.18.1**, proving the platform's *current* node base is 20.18.1. There is no manifest lever that provides node ≥20.19, so the transitive `vite@7.3.6` cannot be satisfied at the image level. The only correct fix is to stop the tree from resolving vite 7.

(Note: eph-sandbox verification of the yarn fix was not possible here — the sandbox base image has no node/yarn toolchain. Diagnosis is from the definitive, repeated build-log engine error plus direct `yarn.lock` inspection; the resolution behavior below is deterministic for yarn v1.)

## Fix (apply in the source / preview environment)
In `frontend/package.json`, add `vite` to the EXISTING `resolutions` block so every consumer (including vitest/vite-node) is forced onto a node-20.18-compatible vite:

```json
"resolutions": {
  "brace-expansion": "^5.0.8",
  "form-data": "^4.0.6",
  "tmp": "^0.2.6",
  "postcss": "^8.5.18",
  "vite": "^6.4.3"
}
```

Then regenerate the lockfile so the transitive range collapses to 6.4.3:
```
cd frontend && yarn install
```
Confirm `grep -A2 'vite@\^5.0.0' yarn.lock` now resolves to a `6.x` version (no `7.3.6` remaining). Commit BOTH `frontend/package.json` and `frontend/yarn.lock`, then redeploy.

### Verify locally (optional)
`cd frontend && yarn install && yarn build` should complete without the engine error. `yarn test` (vitest) still works — vitest 3.2.6 supports vite 6.

### Alternative (only if you intentionally want vite 7)
Keep vite 7 and instead move the app off node 20.18 — but that depends on the platform node base advancing to ≥20.19, which is outside this deployment's control. The resolutions pin above is the correct, self-contained fix.

## Manifest state note
I left a staged manifest override on this deployment: `config.yaml` with the `FRONTEND_IMAGE` pin removed (functionally a no-op today since the platform default equals the old pin) and the other four template files (`Dockerfile.cloudbuild`, `entrypoint.sh`, `nginx.conf`, `build-frontend-artifacts.sh`) written back verbatim. No revert needed; the next redeploy adopts it cleanly. Do NOT re-add a `FRONTEND_IMAGE` pin.
