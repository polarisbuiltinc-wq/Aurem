**Hypothesis 3 (stale EDGE cache on the custom-domain zone) is the cause.** Hypotheses 1, 2, and 4 are disproven with evidence below. The build ran, produced the new code, and pushed it to R2; the origin/KV pointer is current; the browser at `https://auremcto.com/signup` was served a **stale, edge-cached `index.html`** that still references the PREVIOUS build's content-hashed JS chunks — so the browser never requested the new chunks that contain `CompleteRegistration`/`Lead`.

### H2 — "build ran but ate my changes / source didn't contain the code" → DISPROVEN
Inspected the EXACT source `pull_source` captured for this run (eph sandbox, `/app/scratch` = literal build input):

### H4 — "stale K8s replica serving old build" → NOT APPLICABLE
For `frontend_type = cloudflare`, the web frontend is served from Cloudflare R2 via the edge worker, not from K8s pods. Replica rollout state does not affect served frontend assets.

### H3 — stale edge cache → CONFIRMED by isolation
- Probed the platform origin `https://launch-pad-237.emergent.host/signup` → **200**, and the returned `index.html` head contains current content (`Meta Pixel Code — Iter 388-ag (2026-02-14) · consent gate REMOVED`). Both `emergent.host` and `auremcto.com` are served by the SAME Cloudflare worker + KV version pointer, so the **pointer is current and the origin is fresh**.
- Your grep was against `https://auremcto.com/signup`. Origin fresh + custom-domain stale ⇒ the staleness lives in the **edge cache scoped to the custom-domain hostname**, not in the build or the version pointer.
- Mechanism: JS chunks are **content-hashed** (e.g. `file-text-BunKG8mZ.js`) → immutable, safe to cache forever. `index.html` is **stable-named** and is the file that maps to the current chunk hashes. If the edge serves a stale cached `index.html`, the browser loads the OLD chunk hashes and never fetches the new chunks — exactly your symptom (bundles load fine, substantial size, but lack the new strings).
- This also explains the recurring "picks up on the 2nd deploy" pattern (Iter 388-ah, 388-ai, 389): the post-promote Cloudflare cache purge is **best-effort**; when it lags/misses, the stale `index.html` keeps serving until a later purge or the edge TTL expires — a second deploy fires another purge that succeeds.

## Fix path
1. **Immediate:** hard-purge the Cloudflare edge cache for the auremcto.com zone (specifically the HTML entrypoints: `/`, `/index.html`, and any prerendered route HTML like `/signup` — the build runs `vite build && node scripts/seo-prerender.mjs`, so prerendered route HTML also needs purging). Then re-fetch with cache bypass and re-grep. No rebuild is required — the correct assets are already in R2.
2. **Caching policy (permanent):** ensure stable-named HTML (`index.html` + prerendered route HTML) is served with `Cache-Control: no-cache`/short TTL and is purged on every promote; keep content-hashed chunks immutable (long TTL). The bug is HTML being edge-cached, not the chunks.
3. **Platform reliability (root of recurrence):** the post-promote Cloudflare cache purge is best-effort and is the actual systemic gap. It should be made deploy-blocking (or verified + retried) for HTML entrypoints on all attached custom-domain zones, so a frontend-only change can't be masked by a stale-HTML edge hit.
4. **Guard already half-built in the app:** `frontend/vite.config.js` `resolveBuildSha()` bakes a build sha consumed by `AdminSystemHealth.jsx` to "detect stale-bundle-on-prod". Recommend surfacing served-sha vs expected-sha (and/or a synthetic check that fetches `/signup` post-deploy and asserts the expected chunk hash) so this fails loudly instead of silently.
