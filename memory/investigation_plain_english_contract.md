# Investigation — Plain-English Output Contract for EXPLANATION/ADVISORY Answers (Phase 0)
Date: 2026-08-27 · Preview only · read-only investigation · 6 source files read (routers/chat.py [already read for A0], services/orchestrator.py [AUREM_CTO_PERSONA block], services/house_rules.py, services/feature_flags.py, services/error_translator.py, services/ora_chat/grounding_check.py) · 1 real live probe call (~$0.01) · 0 product-code changes made

## 5-LINE SUMMARY (I1-I5)
- CONFIRMED: the reported register bug happens on the **main chat surface** (`/chat/send` / `/chat/stream`, `body.ora_panel=false`), NOT on Ask Advisor. The system prompt is `AUREM_CTO_PERSONA` (`services/orchestrator.py:618-900+`), whose OWN embedded "MODE DETECTION" block explicitly routes "explain a SPECIFIC file/folder/feature in their repo" into **EXECUTE MODE** (`orchestrator.py:710-715`), and EXECUTE MODE's own rules say "ANSWER WITH REAL DATA. Quote actual line numbers, function names" (`orchestrator.py:754-757`). This mode split is **prompt-text only** — the LLM self-classifies; there is no server-side boolean distinguishing "explain" from "code-change" on this surface (see I3).
- CONFIRMED: an existing prompt-injection hook exists and is reusable — `services/house_rules.py` (`get_active_chat_prompt()` / `format_house_rules_block()`) already appends admin-defined text into `extra_sys` for the main chat surface (`routers/chat.py` ~398-410, `chat_send`). It is currently an admin-global on/off toggle (not user-allowlisted), so it is the right INJECTION POINT but not itself the flag mechanism — `services/feature_flags.py` (`is_enabled(flag, user_id, tier)`, already used for `workcard_*` flags with `user_allowlist`) is the correct flag mechanism to gate a NEW contract block the same way.
- CONFIRMED: `services/error_translator.py`'s LLM-fallback (`_llm_rewrite()`, lines 220-273) is **error-specific**, not a general-purpose "strip jargon" function — it takes a raw error string and produces a fixed `{plain, steps, suggestion}` JSON contract via its own system prompt. It is **not directly reusable as a call**, but its system-prompt PATTERN ("translate for a non-technical founder", explicit token cap, strict output schema) is the direct precedent the new contract should be modeled on. `services/ora_chat/grounding_check.py` is a different, unrelated concern (post-hoc hallucination/fabrication DETECTION via regex, logs to `ora_hallucination_log`) — not a jargon-stripper, but a plausible place to ALSO log "R1-R7 violation" events later using the same pattern, if the founder wants that in Phase 2.
- LIKELY (real live probe, not fully reproducing the founder's exact severity): sent the real question *"how do the agents in my project work? explain it to me simply, im not super technical"* through the real `/chat/send` path (`test_admin_001`, real repo-connected project `ora-grounding`) → got a **493-word / ~656-token** real answer that already reads fairly plainly in tone, but still violates R1 (names `grounding.py`, `review.py`, `redis_lock.py` — real file names) and exceeds R7's ~300-500 token target. This run did NOT reproduce a full 1500-token whitepaper — model output varies by repo/run, and this repo's content is smaller than whatever repo triggered the founder's live incident. The mechanism (EXECUTE-mode "quote real data" instruction) is nonetheless the same one described in the bug report; I did not have a way to reproduce the exact founder session/repo.
- Hand-written R1-R7-compliant rewrite of the SAME real facts: **145 words / ~193 tokens** — a **~3.4x** output-token reduction on this sample (lower than the framed 3-5x, honestly reported; the gap would likely be larger on a repo with more files/agents to enumerate, matching the founder's reported case).

## I1 — Where the answer is generated (file:line)
- Route: `POST /api/aurem-dev/chat/send` (non-streaming) and `POST /api/aurem-dev/chat/stream` (SSE) in `backend/routers/chat.py`. Neither is the Ask Advisor panel (`body.ora_panel` defaults `False`, only set `True` by the dedicated side-panel widget, `routers/chat.py:244-248`).
- Provider/model: routed through the normal chat_with_tools / orchestrator model-routing (not a special "explain" path) — same LLM call as any other chat turn.
- System-prompt assembly for the surface hit in the bug report: `AUREM_CTO_PERSONA` (`backend/services/orchestrator.py:618`), always present for non-`ora_panel` turns. Inside it:
  - `# MODE DETECTION` (`orchestrator.py:697-735`) — self-classifies into (A) CONVERSATIONAL, (B) EXECUTE, (C) INVENTORY. Trigger for (B) EXECUTE explicitly includes `"explain a SPECIFIC file/folder/feature in their repo"` (`orchestrator.py:712-713`).
  - `# HOW TO RESPOND` step 2 (`orchestrator.py:754-757`): `"ANSWER WITH REAL DATA. Quote actual line numbers, function names, and code you fetched."` — this is the literal instruction producing file:line-heavy prose for ANY EXECUTE-mode turn, including pure explanations.
  - The `aurem-handoff` ship-brief fence itself is already correctly gated OFF for explain-only turns (`orchestrator.py:767-791`, negative rules b/c require a mutation verb + a real file-path token) — so **ship/confirm cards are structurally unaffected by this bug already**; the violation is in the free-text answer body, not the handoff brief.

## I2 — Existing hook to reuse (reuse-vs-new)
- **REUSE, don't build new**: `services/house_rules.py` → `get_active_chat_prompt()` + `format_house_rules_block()`, already wired into `chat_send`'s `extra_sys` assembly. This is the correct INJECTION POINT for an R1-R7 instruction block.
- **REUSE for the flag**: `services/feature_flags.py::is_enabled(flag, user_id, tier)` — same allowlist/rollout mechanism already used for `workcard_*` flags (per PRD). A new flag (e.g. `explain_plain_english_v1`) with `user_allowlist=["test_admin_001"]` matches the requested "default OFF, allowlist test_admin_001" exactly, with zero new schema.
- Both mechanisms already exist and compose cleanly: `if await is_enabled("explain_plain_english_v1", ...): extra_sys += PLAIN_ENGLISH_CONTRACT_BLOCK` — no new endpoint, no new collection, additive only.

## I3 — Is there already an explain-vs-code-change switch? (ANSWER: PARTIAL / UNCERTAIN for main chat)
- **CONFIRMED, code-level, exists today**: Ask Advisor (`body.ora_panel == True`) IS a real server-side boolean — but it is the WRONG surface for this bug (the bug is on main chat) and, worse, `ORA_PANEL_TONE`'s own R1 ("READ BEFORE WRITE... file path, version number, line count... MUST have a corresponding read_repo_file call") explicitly **encourages** citing file paths in the visible answer — Ask Advisor is not already a plain-English surface either.
- **UNCERTAIN for main chat**: the EXECUTE vs CONVERSATIONAL split that actually matters here is **prompt-text only** (`orchestrator.py`'s own "MODE DETECTION" section) — the model self-classifies; there is no server code that reads the classification back out. This means Phase 1 cannot simply gate on an existing server variable for "is this an explain turn on main chat" — it would need either (a) a new lightweight heuristic (e.g., reusing the SAME mutation-verb/file-path-token regex logic that already gates the `aurem-handoff` fence, inverted: no mutation verb + repo/feature reference → treat as explain-leaning) or (b) always injecting the plain-English instruction and trusting the model's own EXECUTE/CONVERSATIONAL split to keep code-change answers technical (since the instruction below would say "for explanations only"). Recommend labeling this **the single open design question for Phase 1** rather than assuming either approach — founder input welcome on which.
- Ship/confirm cards (`PlanApprovalCard.jsx` / `ShipPendingCard.jsx`, per existing PRD) render from the **separate structured plan/handoff-brief data path**, not from this same free-text `content` field — so whatever explain-only contract is injected into `extra_sys`, it cannot leak into those cards by construction (different code path). This is **LIKELY**, not re-verified by reading those two frontend files fresh this session (out of the 6-file cap) — should be confirmed with a real T2 test in Phase 2, not assumed.

## I4 — Is there a reusable "strip jargon" helper?
- **NO direct reusable function.** `services/error_translator.py::_llm_rewrite()` (line 220) is a fixed-purpose error→`{plain,steps,suggestion}` JSON translator with its own system prompt (line 231-242) — tightly coupled to the error-report shape, not a generic text-simplifier. Cannot be called as-is on arbitrary explanation text.
- **REUSABLE AS A PATTERN**: the same system-prompt techniques apply directly — audience framing ("for a non-technical founder"), a hard output token cap, and a strict format contract. Phase 1's R1-R7 block should be modeled on this precedent rather than inventing a new one from scratch.
- `services/ora_chat/grounding_check.py` is unrelated (hallucination/fabrication detection, not jargon-stripping) — noted only because it's the closest existing "check the model's own output shape" infrastructure, in case Phase 2 wants a similar audit log for contract violations (founder's call, not assumed).
